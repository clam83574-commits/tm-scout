# Развёртывание tm-scout

Два куска с разными требованиями, поэтому и площадки разные.

| Кусок | Что требует | Где живёт |
|---|---|---|
| Сборщик `scout.py` | Chromium + ~48 мин на прогон | GitHub Actions |
| Бот `bot.py` | постоянная доступность, миллисекунды на ответ | Cloudflare Workers |

Почему не одна площадка: у сборщика нужен настоящий браузер (Transfermarkt
закрыт AWS WAF) и почти час работы — это не лезет ни в одну бессерверную
функцию. У бота наоборот: ему нужна не длительность, а то, чтобы он отвечал
всегда, в том числе когда ноутбук выключен.

Netlify не подходит для сборщика в принципе: функции живут секунды,
Chromium недоступен. Бота он потянул бы, но базы данных у него нет, и
данные пришлось бы зашивать в сборку при каждом обновлении.

---

## 1. Сборщик на GitHub Actions

Бесплатно: 2000 минут/мес на приватные репозитории. Наш прогон — 48 минут
раз в неделю, около 200 минут в месяц.

**Отдельный репозиторий, не `ibix-studio`.** Студийный репозиторий — это
push-only бэкап базы знаний, ему не место в CI, и секреты клиентского
продукта там хранить не нужно.

```bash
# из products/tm-scout
git init
git add scout.py bot.py diff.py requirements.txt README.md deploy/
mkdir -p .github/workflows && cp deploy/crawl.yml .github/workflows/crawl.yml
git add .github/workflows/crawl.yml
git commit -m "tm-scout: сборщик, бот, недельный дифф"
```

Дальше создать приватный репозиторий `tm-scout` на GitHub и запушить.

Расписание — понедельник 03:00 UTC, плюс кнопка «Run workflow» для ручного
запуска. Результат (`out/candidates.csv`, `.json`, `weekly-diff.md`)
коммитится обратно в репозиторий, база кладётся в артефакты на 90 дней.

Тонкость: GitHub отключает расписание после 60 дней без активности в
репозитории. Нас это не касается — каждый прогон коммитит результат,
то есть активность создаёт сам.

## 2. Бот на Cloudflare Workers

`bot.py` переписан на JS (`worker/src/index.js`): Workers не выполняют наш
Python — `requests` и `sqlite3` там недоступны. Навигация, три независимых
переключателя категорий, сортировки и поиск перенесены один в один, потому
что D1 — это тот же SQLite и запросы остались на SQL.

Заодно бот переведён с long polling на вебхук: Telegram сам стучится в
Worker, постоянный процесс больше не нужен. Вебхук подписан заголовком
`secret_token` — без него в Worker мог бы постучаться кто угодно.

**Две команды, всё остальное делает скрипт:**

```bash
npx wrangler login      # ОДИН РАЗ, в обычном терминале — вход в аккаунт
node setup.mjs          # из папки worker/
```

`setup.mjs` создаёт базу D1, вписывает её id в `wrangler.toml`, заливает
кандидатов, кладёт секреты (токен берёт из `.env`, секрет вебхука генерирует
сам), публикует Worker, вешает вебхук и показывает отчёт Telegram о нём.
Скрипт идемпотентный — можно запускать повторно.

Проверка кода до деплоя: `node test.mjs` — 17 проверок экранов на настоящей
локальной базе D1, без сети и без аккаунта.

Чтобы недельный прогон сам обновлял базу бота, в секреты репозитория GitHub
кладутся `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` — шаг заливки в D1
в workflow уже написан и включится сам, как только секреты появятся.

## Что нужно от владельца

Ровно два действия, оба — подтверждение личности, за него их сделать нельзя:

1. `npx wrangler login` — вход в Cloudflare.
2. Создать приватный репозиторий `tm-scout` на GitHub и запушить туда код
   (или `gh auth login`, если ставить GitHub CLI).

Плюс, когда будет удобно: Telegram id тех, кому можно пользоваться ботом
(`/whoami` в боте) — вписать в `TM_BOT_ALLOW` и переопубликовать.

## Пока всё это не сделано

Бот работает с ноутбука владельца (`python bot.py`) и жив, пока ноутбук
включён. После перехода в Cloudflare локального бота надо остановить:
два процесса будут драться за одни и те же апдейты.
